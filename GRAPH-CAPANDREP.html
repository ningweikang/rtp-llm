⚡ 图执行：捕获（Capture）→ 实例化（Instantiate）→ 重放（Replay）

CUDA GraphACL Graph (昇腾) 一次录制 · 多次播放RTP-LLM decode 图模式

① 捕获 Capture

Host 把固定算子序列逐个下发并"录制"。绑定的是 kernel 顺序、依赖、参数和内存指针，产出 cudaGraph_t（图描述）。

② 实例化 Instantiate

cudaGraphInstantiate 把图描述编译为 cudaGraphExec_t（优化后可执行图）。真正执行的是 Exec 版本。

③ 重放 Replay

之后每次只需一次 cudaGraphLaunch(exec, stream)，GPU 上算子排队连续执行，CPU 不再逐个提交 kernel。

④ 为什么快

1000 个 kernel：传统 = 1000 次 CPU 调度；Graph = 1 次 Graph Launch。减少 Python 调度、dispatcher、runtime launch、driver 交互。

⑤ 核心限制

执行路径固定、memory address 固定（Graph 绑定指针而非 tensor 名）、layout 固定。动态量需特殊处理。

⑥ 与 LLM 结合

decode 每 token 的 Attention→MLP→AllReduce 序列固定，每个 token 一次 Graph Replay。vLLM/TensorRT-LLM 维护 Graph Pool（按 batch 分桶）。

🧩 动态输入怎么处理？

LLM 的 batch size / seq len 是动态的，但 Graph 需要固定 shape、固定内存、固定 kernel 路径。三种常用方案如下。
💡 注意：Graph Pool 里多张图并不是懒加载 —— 它们在服务启动时一次性全部捕获完成（RTP-LLM 的 initCapture()），捕获顺序从大到小以确定内存池高水位；请求 batch 超过已捕获最大值时 fallback 到普通模式。

方案一 · 固定 Shape + Padding

所有请求用同一张图，不足的 slot 用 padding 填充
batch=8, seq_len=8192 固定一张图 → 任意请求都 padding 到该 shape 后 replay。简单但浪费算力。

方案二 · 多 Graph Cache（Graph Pool）

按 batch size 分桶建多张图，请求按 batch 选图，不足则 padding

🔍 Profiler 中如何判断 Graph 是否生效

同样的 kernel 序列，两种模式在 profiler 时间线上的形态截然不同。

Eager 模式 PyTorch → Runtime → Kernel

Host Runtime 调用多 kernel 间存在间隙 CPU 调度明显

Graph 模式 PyTorch → Graph Execute → Nodes

Graph Launch / Replay 事件 Host runtime 减少 kernel 连续执行 · GPU idle 减少

❓ 自检（点击展开）

Eager 下每个 kernel 都要经 CPU 调度 → 设置参数 → 提交 kernel 三步，且 1000 个 kernel = 1000 次调度。
图模式把整个序列录成一张图，replay 时 CPU 只提交一次（cudaGraphLaunch），GPU 按图内依赖直接执行完整 pipeline。减少的不仅是 runtime launch，还有 Python 调度、PyTorch dispatcher、driver 交互 整条链路。
cudaGraph_t = 图结构描述（记录节点、依赖、参数）；cudaGraphExec_t = 优化后的可执行图（经 cudaGraphInstantiate 编译）。
真正执行的是 Exec 版本；描述版本可以反复修改/重新实例化。对应到昇腾侧，NPUGraph 捕获后同样要先实例化才能 replay。
Graph 绑定的是 memory address（指针）而不是 tensor 名称。捕获时 Q 在 0x100000，图就记住 0x100000；replay 时即使 Q 挪到了 0x900000，图 仍访问 0x100000（旧地址的过期数据，甚至非法地址崩溃）。
所以要求：tensor storage 固定、memory allocation 固定、pointer 地址稳定。这也是 RTP-LLM 用 CaptureMemoryHold 在捕获期保持 tensor 生命周期、并用静态缓冲池的原因。
三方案：① 固定 shape（所有请求 pad 到同一 shape，简单但浪费）；② 多 Graph Cache / Graph Pool（按 batch=1/2/4/8 各建一张图，请求按 batch 选图，不足 padding —— 上方方案二可交互操作）；③ Graph Update（cudaGraphExecKernelNodeSetParams 改参数值，但 不能改 kernel 数量 / dependency / memory allocation）。
LLM 输入天然动态（batch / seq / context length / KV offset），所以 vLLM / TensorRT-LLM 维护 Graph Pool，按 batch size 选图执行。

⚙️ 实现细节：Pool 里的多张图在服务启动时一次性全部捕获（RTP-LLM 的 initCapture() → captureDecode()），捕获顺序从大到小（先确定内存池高水位，小图复用同一块池）；每个 bucket 捕获后立即 replayAndSyncCheck 验证。启动变慢换来运行期零捕获开销；batch 超过已捕获最大值时 fallback 普通模式。
机制同构、实现不同：都是 capture → instantiate → replay，消除 Host 调度。
差异在设备层 API：NPUGraph/NPUStream vs CUDAGraph/CUDAStream。本仓库 rtp_llm/cpp/ascend_graph/ 用 ascend_graph_device_shims 把 ACL 原语封装成与 CUDA 版一一对应的接口，Runner 逻辑几乎原样复用 —— 这就是"对标 CudaGraphRunner"的依据。
Eager：时间线上 Host Runtime 调用密集、kernel 之间有 间隙、CPU 调度明显。
Graph：出现 Graph Launch / Replay 事件、Host runtime 调用大幅减少、kernel 连续执行、GPU idle 减少。对照上方 Profiler 对比区查看。
